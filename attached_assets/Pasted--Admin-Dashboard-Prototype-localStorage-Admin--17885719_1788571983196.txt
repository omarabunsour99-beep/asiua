أريد تحويل الـAdmin Dashboard الحالي في هذا المشروع من Prototype يعتمد على localStorage إلى **Admin Dashboard حقيقي، محمي، ومربوط بقاعدة بيانات PostgreSQL**.

## ⚠️ قواعد مهمة جدًا قبل البدء

* لا تعيد بناء الموقع من الصفر.
* لا تعيد تصميم الموقع العام.
* لا تحذف الموقع الحالي أو بياناته الحالية.
* لا تستبدل الـAdmin الحالي بالكامل.
* حافظ على `/admin` كمسار الـAdmin.
* استخدم واجهة الـAdmin الحالية كأساس وطوّرها.
* لا تستخدم localStorage كمصدر أساسي لبيانات المحتوى بعد تنفيذ النظام الجديد.
* لا تجعل البيانات العامة تعتمد على `src/lib/data.ts` بعد نقل المحتوى إلى قاعدة البيانات.
* لا تنشئ duplicate models إذا كان هناك شيء موجود يمكن إعادة استخدامه.
* لا تضف نظام تحميل للحلقات.
* لا تضف Download Links أو Download URLs أو Download buttons أو أي نظام Download.
* لا تضف نظام Quality.
* لا تضف 360p / 480p / 720p / 1080p كحقول.
* لا تضف arbitrary code editor داخل الـAdmin.
* لا تغير الـbranding الحالي للموقع.
* لا تستخدم بيانات أو روابط أو branding من أي موقع خارجي.
* قبل تعديل الملفات، افحص المشروع والبنية الحالية بالكامل.

## المرحلة 1 — فهم المشروع الحالي

* `artifacts/asian-screen`

أنت تعرف من الفحص السابق أن:

* الـAdmin الحالي Prototype.

## المرحلة 2 — Database Schema

أنشئ schema حقيقي في PostgreSQL باستخدام نفس نظام database/ORM الموجود في المشروع، ويفضل Drizzle إذا كان هو المستخدم حاليًا.

أنشئ models مناسبة على الأقل لـ:

### Admin Users

* id
* username أو email
* passwordHash
* role
* createdAt
* updatedAt

لا تخزن passwords كنص عادي.

Role يجب أن يكون قابلًا للتوسع مستقبلًا، مثل:

* admin

### Series / Titles

استخدم model واحد مناسب للمحتوى إذا كان التصميم الحالي يعتمد على Title، أو افصل Series وMovies فقط إذا كان ذلك أفضل ومتوافقًا مع المشروع.

البيانات المطلوبة للمحتوى:

* id
* title
* originalTitle
* slug
* description
* type
* country
* year
* status
* rating
* poster
* backdrop
* language
* director
* cast
* trailer
* createdAt
* updatedAt

Type يجب أن يدعم على الأقل:

* series
* movie

Status يجب أن يدعم:

* upcoming
* airing
* completed

ويجب أن تكون القيم قابلة للعرض بالعربية في الـAdmin والموقع.

## المرحلة 7 — API

طوّر `artifacts/api-server` لإضافة API حقيقي لإدارة المحتوى.

أضف endpoints منظمة للمصادقة والمحتوى.

مثلًا:

### Authentication

POST `/api/auth/login`

POST `/api/auth/logout`

GET `/api/auth/me`

### Series

GET `/api/admin/series`

GET `/api/admin/series/:id`

POST `/api/admin/series`

PATCH `/api/admin/series/:id`

DELETE `/api/admin/series/:id`

### Seasons

GET `/api/admin/series/:id/seasons`

POST `/api/admin/series/:id/seasons`

PATCH `/api/admin/seasons/:id`

DELETE `/api/admin/seasons/:id`

### Episodes

GET `/api/admin/seasons/:id/episodes`

POST `/api/admin/seasons/:id/episodes`

PATCH `/api/admin/episodes/:id`

DELETE `/api/admin/episodes/:id`

### Watch Links

POST `/api/admin/episodes/:id/watch-links`

PATCH `/api/admin/watch-links/:id`

DELETE `/api/admin/watch-links/:id`

استخدم conventions الموجودة في المشروع إذا كانت مختلفة، ولا تكرر APIs بلا داعٍ.

لا تنشئ أي Download API.

## المرحلة 8 — Authentication حقيقي

الـAdmin الحالي غير محمي.

أريد Authentication حقيقي.

يجب أن:

* `/admin` لا يكون متاحًا للإدارة بدون تسجيل دخول.
* لا تعتمد الحماية على إخفاء الصفحة في frontend.
* كل عمليات POST/PATCH/DELETE يجب أن تتحقق من صلاحيات المستخدم على server.
* password يجب أن يكون hashed.
* استخدم session/cookie آمن أو النظام المناسب للـstack الحالي.
* لا تخزن password في localStorage.
* لا ترسل passwordHash إلى frontend.
* لا تعرض secrets.
* لا تضع DATABASE_URL أو أي secret داخل frontend.

إذا لم يوجد auth framework مناسب، استخدم أبسط حل آمن ومتوافق مع المشروع بدل إضافة نظام ضخم بلا داعٍ.
